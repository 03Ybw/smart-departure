# Smart Departure

희망 도착 날짜·시각과 여유시간을 고려하여 버스·지하철·도보 경로의 출발시각을 추정하는 대학 프로젝트입니다. **3단계 실연동 검증을 완료했습니다.** 2026-11-14 KST에 부평역[수도권1호선] → 인하대학교 정문을 두 차례 실제 검증했으며, 3단계 누적 사용량은 POI 4회·Transit 2회입니다. 현재 조회 소요시간 기반 추정이며 미래 운행편 시간표 기반 추천은 아닙니다. 검증 후 실제 호출은 다시 비활성화했습니다.

## 3단계 실행 및 기능

지원 중인 **Node.js LTS 22 이상**에서 다음 명령으로 실행하고 **http://127.0.0.1:3000**에 접속합니다. 외부 의존성이나 빌드는 없습니다. 종료는 Ctrl+C입니다.

```powershell
npm run dev
npm test
```

**API 키 없이도 화면과 목표 도착시각 계산은 사용할 수 있습니다.** 장소 검색과 경로 조회는 기본 비활성화입니다. 입력할 때 자동 호출하지 않으며 각 장소의 검색 버튼과 별도의 경로 조회 버튼을 눌러야 서버 API에 요청합니다. 활성화하지 않은 상태에서는 한국어 안내를 표시하고 외부 요청은 하지 않습니다. 폰트·화면 자산은 로컬에서 제공합니다.

- 검색 결과 최대 5개 중 사용자가 주소를 확인하여 직접 선택합니다. 첫 결과를 자동 선택하지 않으며 특정 구간을 고정하지 않습니다.
- POI 입구 좌표 `frontLon/frontLat`을 우선 사용하고 유효하지 않으면 중심 좌표 `noorLon/noorLat` 한 쌍을 검증하여 사용합니다. 중심 좌표 사용 여부를 표시합니다. 좌표 누락·범위 초과·`(0, 0)` 등은 제외하며 두 종류의 좌표를 섞지 않습니다.
- 장소명 수정·재검색·선택 변경·일정 변경 시 기존 추천을 제거합니다. 장소명 수정이나 검색 실패 시 이전 장소 선택도 해제합니다. 진행 중 요청 취소와 요청 순서 검사로 오래된 응답을 무시합니다.
- 버스·지하철·도보 구간별 승하차 지점과 소요시간, 전체 소요시간, 도보시간, 환승 횟수, 추정 출발 날짜·시각을 표시합니다. 데이터가 없으면 추정값을 표시하지 않습니다.
- 희망 도착 날짜·시각과 여유시간이 유효하면 **목표 도착시각을 즉시 자동 계산**합니다. 별도의 목표 계산 버튼은 제거했습니다. 여유시간 변경은 항상 원래 희망 도착시각을 기준으로 계산합니다.
- 목표 도착시각은 장소 선택과 독립적입니다. 장소 수정·재선택 시 목표는 유지하고 기존 경로·추정 출발시각만 무효화합니다. 일정 입력이 비어 있거나 유효하지 않으면 계산값을 숨기며, 입력 중에는 새로운 오류 메시지를 표시하지 않습니다. 명시적 경로 조회 시에는 필요한 입력 오류를 안내합니다.
- 검색 버튼과 '경로 조회하고 출발시각 추정' 버튼을 유지합니다. 자동 목표 계산·입력 변경·Enter 제출로 외부 API를 호출하지 않습니다. 기존 디자인과 반응형 CSS도 유지합니다.

### API 구성과 키 설정

브라우저는 동일 출처 내부 API만 호출하며 외부 요청과 키 사용은 Node.js 서버에서 처리합니다.

| 내부 API | 외부 API 및 처리 |
| --- | --- |
| `GET /api/places?q=검색어` | `GET https://apis.openapi.sk.com/tmap/pois`. `version=1`, `searchType=all`, `page=1`, `count=5`, `reqCoordType=resCoordType=WGS84GEO`, `searchtypCd=A`; 검색어 URL 인코딩 |
| `POST /api/recommendation` | `POST https://apis.openapi.sk.com/transit/routes`. 기존 `buildRequest`, `computeRoutes`, `analyzeResponse` 재사용. 선택 좌표로 `count=5`, `lang=0`, `format=json`; **searchDttm 생략** |

두 외부 API 모두 `appKey` 헤더를 사용합니다. POI는 [공식 요청 문서](https://tmap-skopenapi.readme.io/reference/장소통합검색)와 [공식 응답 샘플 설명](https://tmap-skopenapi.readme.io/reference/poi-검색-샘플예제), 대중교통은 [공식 경로 문서](https://transit.tmapmobility.com/docs/routes)를 기준으로 구현했습니다.

최상위 `.env`는 **서버에서만** 읽습니다. 기존 `.env`를 덮어쓰지 말고 필요한 변수만 로컬 편집기로 추가하세요. `.env.example`에는 실제 키가 없습니다.

| 변수 | 기본값과 의미 |
| --- | --- |
| `TMAP_APP_KEY` | 대중교통 경로 키. 기본값 없음 |
| `TMAP_POI_APP_KEY` | 선택적인 별도 POI 키. 없으면 `TMAP_APP_KEY` 사용 |
| `ENABLE_LIVE_POI` | `false`. POI 실호출 허용 여부 |
| `ENABLE_LIVE_TRANSIT` | `false`. 대중교통 실호출 허용 여부 |
| `STAGE3_POI_MAX_CALLS` | `0`. POI 누적 최대 승인 횟수 |
| `STAGE3_TRANSIT_MAX_CALLS` | `0`. 대중교통 누적 최대 승인 횟수 |

**대중교통 키의 성공이 POI 이용 권한을 보장하지 않습니다.** 실제 POI 상품 권한, 앱과 키의 연결, 계정 사용량·요금은 사용자 대시보드에서 확인해야 합니다. 이번에는 해당 권한과 현재 잔여량을 확인하지 않았으며 키 재발급·상품 활성화·결제도 수행하지 않았습니다. 프로세스 환경변수가 `.env`보다 우선하며 설정 변경 후 서버를 재시작해야 합니다.

### 실호출 승인과 누적 예산

실호출은 **사용자 승인 후**, 해당 서비스 활성화 값을 `true`로 지정하고 0보다 큰 누적 최대 승인 횟수를 설정해야 가능합니다. 키만 존재하거나 버튼만 눌러서는 기본 설정에서 외부 API를 호출할 수 없습니다. 승인 전에는 기본값을 유지하세요.

- POI는 `reports/stage3-poi-budget.json`, 대중교통은 `reports/stage3-transit-budget.json`에 요청 시작 전 횟수·예약시각을 기록합니다. 예산은 일일 자동 초기화가 없는 **누적 상한**이며 성공·실패·시간초과·이미 시작된 취소 요청을 모두 포함합니다.
- 프로세스 재시작 후에도 기록을 유지합니다. 기록 손상·잠금 중에는 호출을 차단합니다. 예산을 지우거나 매 실행마다 되돌리지 않습니다. 자동 재시도와 한 버튼으로 여러 외부 요청을 보내는 동작은 없습니다.
- 동일 요청의 동시 수행을 막고 완료 후 3초 동안 반복 요청을 차단합니다. 같은 검색어의 최근 결과는 브라우저에서 재표시할 수 있습니다.
- **기존 `reports/tmap-live-budget.json`의 6회 기록과 1단계 CLI 한도는 변경하지 않았습니다.** 예산 확대는 별도 승인이 필요합니다. 오프라인 개발에서는 3단계 예산을 사용하지 않았으며 아래 실연동 검증에서 POI 2회·Transit 1회를 누적 기록했습니다.
- [대중교통 무료체험 한도는 하루 10건](https://transit.tmapmobility.com/terms)입니다. 계정 현재 잔여량이나 POI 한도가 아닙니다. 실호출 전 각 상품의 적용 한도와 다른 도구 사용량을 확인해야 합니다.

### 경로 선택과 계산의 의미

최대 5개 반환 후보를 제공자 순서대로 검사하여 **WALK/BUS/SUBWAY로만 구성되고 대중교통 구간이 있는 첫 유효 경로**를 선택합니다. 최단·최적 경로라고 주장하지 않습니다. 후보가 모두 미지원 수단이거나 필수 데이터가 없으면 오류를 안내하며 경로를 만들지 않습니다.

```text
목표 도착시각 = 희망 도착시각 - 여유시간
추정 출발시각 = 목표 도착시각 - API totalTime(초)
```

도보시간 중복 가산이나 임의 환승 대기시간 추가는 없습니다. 초 단위 계산값은 보존하고 화면 표시는 이전 분으로 내립니다. 목표 도착 `13:50:00`, 소요시간 `727초`이면 계산값은 `13:37:53`, 표시는 `13:37`입니다. 기존 한국시간 유틸로 브라우저 시간대와 관계없이 자정·월말·연말·윤년을 처리합니다. 여유시간 변경 후 목표 도착시각을 다시 계산하며 사용자가 새 경로 조회를 요청해야 새 이동시간을 사용합니다.

**현재 조회 소요시간 기준 추정입니다. 실제 미래 운행편의 출발·도착시각은 확인되지 않았습니다.** 미래 배차, 환승 대기, 교통 지연에 따라 이동시간이 달라질 수 있습니다. `searchDttm`을 희망 도착시각으로 보내지 않으며 실제 시간표와 확정 출발시각을 생성하지 않습니다. 데이터의 `estimateBasis`는 `CURRENT_ROUTE_DURATION`입니다.

### 보안·데이터 관리

선택 가능한 장소는 서버 메모리에 최대 100개, 10분 동안 유지하고 임의 토큰으로 참조합니다. 추천 요청의 좌표를 클라이언트에서 신뢰하지 않고 토큰과 선택 장소명을 확인합니다. 브라우저의 장소 선택·검색 결과와 추천 표시도 10분 후 만료합니다. 서버 재시작·선택 만료 시 다시 검색해야 합니다.

API 원본은 메모리에서 처리하며 파일·fixture·문서에 저장하지 않습니다. 브라우저 저장소도 사용하지 않습니다. 예산 파일에는 서비스 데이터나 키를 넣지 않습니다. [TMAP 이용약관의 저장·재사용 제한](https://transit.tmapmobility.com/terms)을 따라 저장된 데이터를 24시간 이상 사용하지 않으며 장기 경로 캐시를 만들지 않았습니다.

서버는 `127.0.0.1`에만 바인딩하고 공개 자산을 명시적으로 제한합니다. 비공개 파일 HTTP 접근 차단을 유지합니다. 내부 API는 Host·Origin·교차 사이트 요청을 검사하고 JSON 본문을 8KiB로 제한합니다. 외부 URL은 고정하며 리디렉션을 허용하지 않습니다. 요청 시간초과, 한국어 오류 분류와 키 가림 처리를 적용했습니다. CSP는 `connect-src 'self'`로 동일 출처 API만 허용하며 CORS를 개방하지 않습니다. 외부 장소명·주소는 `textContent`로 표시합니다.

**기존 45개 + 신규 42개 = 87개 테스트 통과**를 확인했습니다. 기존 API 검증 소스·시간 유틸·예산·합성 fixture는 보존했습니다. 기존 정적 서버 보안 테스트에서 CSP 기대값만 동일 출처 API 허용에 맞게 조정했습니다. 테스트는 가짜 fetch만 사용하고 실제 TMAP 요청은 하지 않습니다.

목표 도착시각 자동 계산 개선에서는 `tests/automatic-arrival.test.mjs`에 11개를 추가하여 **총 98개가 통과**했습니다. 자동 계산·원래 시각 기준 여유시간 재계산·장소 변경·입력 누락·추천 무효화·날짜 경계를 검증합니다. Chrome에서 자동 계산, 입력 중 조용한 안내, 장소 미선택 상태, 비동기 지연·실패, 320~1360px 반응형도 확인했습니다. 브라우저 API는 별도 합성 서버로 검증했으며 이번 UI 개선의 실제 외부 API 호출은 0회입니다.

오프라인 검증에서는 실제 Chrome 헤드리스에서 기본 비활성화 안내, 합성 장소 검색·수동 선택·추천 전체 흐름, 727초 계산, 여유시간 변경, 늦은 응답 무시, 실패 후 이전 결과 제거, 안전한 텍스트 표시, LA 시간대, 1360/768/390/320px 반응형과 10분 만료를 확인했습니다. 당시 화면 JavaScript 오류와 외부 HTTP 요청은 없었습니다. 아래 실연동 결과와 구분하며 실제 모바일 기기와 다른 브라우저는 별도 검증이 필요합니다.

키 설정과 상품 신청 절차는 [SK OPEN API 이용절차](https://transit.tmapmobility.com/guide)와 [TMAP 이용절차](https://transit.tmapmobility.com/guide/procedure)를 참고하세요. 과거 3회는 `INVALID_API_KEY`였으나 2026-11-13 15:31 KST 재검증에서는 인증과 기본 경로 조회가 성공했습니다. 이전 오류의 정확한 원인이나 해소 원인은 확정하지 않았습니다.

## 실제 검증 실행

**`--live`를 명시한 경우에만 네트워크 요청을 수행합니다.** 자동 재시도는 없으며 API 오류·네트워크 오류·무경로가 발생하면 후속 시나리오를 중단합니다.

```powershell
# 전체 시나리오: A 현재 기준, B 다음 평일 13:50, C 같은 날 13:40
npm run verify:transit -- --live --scenario all

# A만 실행: searchDttm 생략
npm run verify:transit -- --live

# 검색 기준시각 지정: 예시 날짜는 실행일에 맞게 바꾸세요.
npm run verify:transit -- --live --date 2026-11-16 --time 13:50
npm run verify:transit -- --live --search-dttm 202611161340 --count 1
```

최초 검증은 **최대 3회**로 제한했고, 후속 재검증 1회에 이어 사용자가 지정한 미래 조회 2회만 추가 허용해 누적 6회가 되었습니다. 기존 `reports/tmap-live-budget.json`의 attempts 목록에 계속 기록하며, 이번 2회의 한시적 승인 범위(누적 4→6회)는 같은 파일의 authorizations에 기록했습니다. 초기화나 자동 재시도는 없습니다. 이번 추가 예산은 모두 소진했고 기본 CLI의 3회 제한은 유지되어 위 실제 실행 명령은 현재 차단됩니다.

호출 전에 [공식 무료체험 하루 10건 한도](https://transit.tmapmobility.com/terms)와 로컬 기록 4회를 확인했고 이번 2회까지 기록상 6회입니다. 계정 대시보드의 다른 도구 사용량과 전체 잔여량은 확인하지 못했습니다. 추가 실행은 새 요청 범위·한도 확인 후 진행해야 합니다.

세 번째 전송 추적에서는 키 전달이 정상임에도 HTTP 403 / INVALID_API_KEY, Forbidden을 받았으나, 2026-11-13 15:31:51 KST의 기본 조회는 성공했습니다. 15:44:56·15:44:57 KST에는 같은 공식 예시 좌표로 searchDttm=202611161340 및 202611161350을 각각 1회 요청했습니다. 모두 HTTP 200, 비어 있지 않은 itineraries 배열과 경로 1개를 확인했습니다. 이전 인증 오류가 해소된 세부 원인은 미확정입니다.

| 비교 항목 | 미래 13:40 | 미래 13:50 |
| --- | --- | --- |
| 경로 개수 | 1 | 1 |
| totalTime | 727초(12분 7초) | 727초(12분 7초) |
| totalWalkTime / 환승 횟수 | 394초 / 1회 | 394초 / 1회 |
| 구간 | 도보→지하철→도보→버스→도보 | 동일 |
| 지하철·버스 service | 모두 1 | 모두 1 |
| 노선·승하차 지점·수단 기준 경로 차이 | 두 응답에서 차이 없음 | 동일 |
| 실제 운행편 절대 출발·도착시각 | 확인되지 않음 | 확인되지 않음 |

시간 차이는 0초이며 구간별 소요시간도 같았습니다. 두 시각의 동일 결과만으로 모든 미래 조건의 특성이나 배차 반영 여부를 일반화하지 않습니다. searchDttm은 희망 도착시각이 아니라 지정 시각의 운행 여부를 확인하는 검색 조건입니다. 2단계에서는 경로·운행 정보 표시와 명시적인 소요시간 기반 추정 범위를 검토할 수 있지만, 실제 시간표 기반 정확한 출발시각 역산은 추가 데이터가 필요합니다.

## 좌표와 시간

기본 좌표는 [공식 API 문서](https://transit.tmapmobility.com/docs/routes)의 **Request Sample**에서 가져왔습니다.

| 필드 | 값 | 의미 |
| --- | --- | --- |
| startX | 127.02479803562213 | 출발 경도 |
| startY | 37.504585233865086 | 출발 위도 |
| endX | 127.03747630119366 | 도착 경도 |
| endY | 37.479103923078995 | 도착 위도 |

WGS84 X=경도(-180~180), Y=위도(-90~90)를 검증합니다. 국내 좌표를 뒤집어 Y에 127 등을 넣으면 거부합니다. 범위만으로 모든 장소의 위치 정확성이나 모든 뒤바뀐 좌표를 검증할 수는 없습니다. 부평역→인하대학교 정문 좌표는 아직 검증하지 않았으므로 임의로 사용하지 않습니다.

검증한 좌표를 사용할 때는 아래 네 인자를 모두 지정하세요.

```powershell
npm run verify:transit -- --start-x 127.02479803562213 --start-y 37.504585233865086 --end-x 127.03747630119366 --end-y 37.479103923078995 --count 1
```

`count`는 1~10 정수(기본 1), `lang=0`, `format=json`입니다. `searchDttm`은 **한국시간 Asia/Seoul의 YYYYMMDDHHmm**이며 UTC로 바꾸어 보내지 않습니다. `--date YYYY-MM-DD --time HH:mm`으로도 생성할 수 있습니다. 전체 시나리오는 실행일 이후 다음 월~금 날짜를 고르며 `--date`로 변경할 수 있습니다. 공휴일은 판정하지 않습니다. Google의 과거 7일/미래 100일 제한은 TMAP에 적용하지 않습니다.

## 결과 해석과 데이터 관리

`searchDttm`은 지정 시각의 **운행 여부**를 `service`로 확인하기 위한 조건입니다. `arrivalTime`이나 실제 운행편의 출발시각 지정 기능으로 취급하지 않습니다. [공식 API 문서](https://transit.tmapmobility.com/docs/routes).

다음 세 항목을 분리하여 평가합니다.

1. 지정 시각에 운행 여부를 확인할 수 있는지.
2. 기준시각 변경 후 경로·전체/구간 소요시간·운행 여부가 달라지는지.
3. 실제 운행편의 출발·도착시각이 있어 희망 도착시간 기준 역산이 가능한지.

현재 공식 응답 스키마에는 실제 운행편 출발·도착 절대시각이 없습니다. 응답에서 시간 관련 필드 이름을 점검하되, 미문서화 필드가 나타나도 의미를 확인하기 전 시간표로 사용하지 않습니다. API를 요청한 `requestedAt`, API의 요청시각 `reqDttm`, 검색 조건 `searchDttm`을 운행편 시각으로 대입하지 않습니다.

분석은 `metaData.plan.itineraries`의 경로 수, `totalTime`, `transferCount`, `totalWalkTime`, 구간별 `mode`, `sectionTime`, `start/end`, `route`, `service`를 다룹니다. `lane` 및 공식 예시의 `Lane` 표기도 처리합니다. WALK/BUS/SUBWAY 밖의 수단은 `otherModes`로 구분하며 누락 값은 `null`과 `missing` 목록에 남깁니다.

콘솔에는 검증 요약과 비교 결과만 출력합니다. 원본 응답, 상세 경로·노선·지점·도형은 파일로 저장하지 않고 메모리에서만 분석합니다. B/C의 경로 구조와 시간·운행 여부는 각각 비교하며, 반환 순서 변경도 차이로 표시될 수 있습니다. 동일 결과가 나와도 정상 기록합니다.

[이용약관](https://transit.tmapmobility.com/terms)은 서비스로 얻은 데이터를 저장 후 24시간 이상 사용할 수 없도록 제한합니다. 실제 응답을 GitHub나 테스트에 넣지 않고, 검증 문서에는 필요한 관찰·결론만 남깁니다. 콘솔을 별도 파일로 리디렉션하여 서비스 데이터를 저장한다면 24시간 이상 재사용하지 말고 삭제하세요. `reports/`에는 횟수·예약시각만 저장하며 경로 데이터나 키를 넣지 않습니다.

오류는 키 누락, 인증/권한, 할당량, 잘못된 입력, 무경로(HTTP 200 오류 포함), 명시적 지역 미지원, 네트워크, 시간초과, 잘못된 응답으로 구분합니다. 무경로와 인증 실패는 지역 미지원의 증거가 아닙니다. 종료 코드는 0(오프라인/경로 반환), 1(오류), 2(키 없음), 3(무경로)입니다.

Git은 `main`, 원격은 `https://github.com/03Ybw/smart-departure.git`입니다. commit/push는 수행하지 않았습니다.

## GitHub 파일 관리

Git에는 실제 개발·실행에 필요한 README.md, .gitignore, .env.example, package.json 및 필요한 의존성 파일, src/, scripts/, tests/와 기타 앱 실행 파일을 포함합니다. 의존성을 추가할 때 필요한 잠금 파일도 함께 관리합니다.

`AGENTS.md`, `docs/api-verification.md`, `.env`, 비밀 환경 파일, 로그·비공개 응답·reports/·tmp/는 로컬에 보존하고 Git에서 제외합니다. `.env.example`은 실제 키 없이 포함합니다. docs/ 전체를 제외하는 규칙은 추가하지 않았으므로 다른 정상 문서는 계속 관리할 수 있습니다.

Commit 전에는 `git status`, `git ls-files`, `git check-ignore`로 포함·제외 상태를 확인합니다. 제외 대상이 이미 추적 중이면 로컬 파일을 유지하는 `git rm --cached -- 파일경로`로 추적만 해제합니다. 로컬 전용 파일을 강제로 추가하지 않으며, Commit·Push는 사용자 승인 후 수행합니다.
